## 兩次失敗的 ACR 建置（值得記錄）

初次嘗試部署時**沒跑 `npm run build`** 就直接送 `az acr build`，連續兩次失敗（run `ck1c` 08:52、`ck1d` 08:04），白花約 10 分鐘。

根因是 CHANGE-110 初版的 `src/instrumentation.ts` 讓 `next build` 失敗：Next.js 為 instrumentation 同時編譯 **edge bundle**，而 edge 沒有 `fs` / `path` / `stream` / `child_process`。初版把守衛寫成早期返回，動態 import 落在條件區塊之外 → webpack DCE 消不掉 → edge bundle 去解析 `pg` 與 `sharp` 而失敗。修正見 [#154](https://github.com/chris-private-workspace/ai-document-extraction-project/pull/154)。

### 診斷陷阱：`az acr task logs` 的 230 行邊界

`az acr task logs` 對**成功與失敗的 run 都**只回 230 行、都停在 `Step 10/56 : COPY --from=deps ...`、都回 exit 1。我因此誤判失敗點在 COPY node_modules，**並據此排除了自己的改動**。

拿上午成功的 `ck1b` 當對照組，才發現 230 行是 log 抓取的邊界而非失敗點。真正的線索在 `az acr task show-run` 的 `runErrorMessage: "failed during run, err: exit status 1"` 加上失敗時間點（4.5 分鐘處，已跑到 `next build`）。

> **教訓**：`type-check`、`lint`、單元測試全過但 `next build` 失敗 —— 這類 bundle／runtime 解析問題只有 build 抓得到。本專案已有 FIX-069（re2-wasm）、FIX-083（pdfkit）兩次先例，這是第三次。**`npm run build` 是部署前必跑的閘。**

## 回滾方式

```bash
az webapp config appsettings set -g RG-RAPOSCM-AIDocProcessing-DEV -n WebApp-RAPOSCM-AIDocProcessing-DEV \
  --settings ENABLE_INTERNAL_SCHEDULER=false
az webapp restart -g RG-RAPOSCM-AIDocProcessing-DEV -n WebApp-RAPOSCM-AIDocProcessing-DEV
```

**只需把開關設回 `false` 並重啟，不必回退映像** —— 排程器不啟用時完全不執行任何程式碼路徑。

若要完整回退映像：

```bash
az webapp config container set -g RG-RAPOSCM-AIDocProcessing-DEV -n WebApp-RAPOSCM-AIDocProcessing-DEV \
  --container-image-name acrscmdocprocessingdev.azurecr.io/ai-document-extraction:dev-change109-20260727143423
```

本次無資料庫改動，回滾無資料相容性顧慮。
