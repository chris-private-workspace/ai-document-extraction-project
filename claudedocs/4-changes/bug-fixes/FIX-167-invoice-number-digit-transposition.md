# FIX-167: 發票號碼字元錯位／插入 —— 非確定性，同一份重跑可能正確

> **建立日期**: 2026-08-05
> **發現方式**: 對發票原文核對（[TEST-REPORT-006 §8.1 / §8.4](../../5-status/testing/reports/TEST-REPORT-006-full-sample-coverage-verification.md)）
> **影響範圍**: Stage 3 欄位提取 `invoice_number`（`stage-3-extraction.service.ts` + Stage 3 Prompt）
> **優先級**: 中（號碼是對外對帳與查詢的主鍵；但金額不受影響，且非必現）
> **狀態**: 📋 規劃中（影響面已量化：Toll 泰國件 5/51 = 9.8%；修法 B 可行性 98.4%）
> **相關**: [FIX-166](FIX-166-vat-extracted-as-line-item-charge.md)（同一輪核對發現、同屬非確定性）、[CHANGE-113](../feature-changes/CHANGE-113-line-item-group-key-multi-shipment-invoice.md)（其階段一 A3 記有側躺頁未轉正時模型讀錯 AWB 字元的實測）

---

## 問題描述

`invoice_number` 出現字元層級的錯誤 —— 錯位或多插字元，其餘欄位（日期、金額、明細）全部正確。

### 累積實例

| 檔案 | 發票原文 | 系統抽出 | 形態 |
|---|---|---|---|
| `NEX_RCEX240692,0692A,0692B_9898.pdf` | `EVJ-F9898` | `EVJ-F9989` | **數字錯位**（9898 → 9989） |
| `TOLL_RCEX250018_56933.PDF` | `TLTH00156933` | `TLTH000156933` | **多插一個 0** |
| `TOLL_RCIM240356_58536.PDF` | `TLTH00158536` | `TLTH000158536` | 多插一個 0 |
| `TOLL_RCIM260031_80791.PDF` | `TLTH00180791` | `TLTH000180791` | 多插一個 0 |
| `TOLL_RCIM260031_80791 (1).PDF` | `TLTH00180791` | `TLTH000180791` | 多插一個 0 |

Nippon 那筆的原文另有檔名尾碼 `_9898` 佐證。Toll 四筆是同一形態在不同文件重複出現（其中兩筆為同一份的重複上傳）。

另有 3 筆「原文找不到相近值」（`DHL_RCEX250281,0282_37434.pdf`、`NEX_RHIM250249_74694.pdf`、`TOLL_RCEX250018` 一類），因文字層或版面因素未能定位原文，**不列入本 FIX**，待補查。

## 已量化 A：影響面 —— Toll 泰國件 9.8%

⚠️ 本節與下節（B）是**兩種不同的量化**：A 問「已處理的文件中有多少份實際錯了」（掃 DB 既有結果），B 問「同一份重跑會不會再錯」（重跑 N 次）。兩者不可互相取代。

2026-08-05 掃描全部 93 份 `TOLL_` 文件（79 份有號碼）：

| 號碼格式 | 份數 | 異常 |
|---|---:|---:|
| 泰國 `TLTH001…` | 51 | 🔴 **5（9.8%）** |
| 香港 `TLHKHKG009…` | 28 | 0 |

異常清單（正確形態為 `TLTH001` + 檔名尾碼 5 位 = 12 字元；異常者多插一個 `0` 成 13 字元）：

```
TOLL_RCEX250018_56933.PDF        → TLTH000156933
TOLL_RCIM240356_58536.PDF        → TLTH000158536   （同檔名重複上傳 2 份，皆錯）
TOLL_RCIM260031_80791.PDF        → TLTH000180791
TOLL_RCIM260031_80791 (1).PDF    → TLTH000180791
```

與初版所列的 4 個檔名完全一致，另補上重複上傳的那一份。

### 🔴 這改變了修法 C 的設計

**同一家 Toll 有兩種號碼格式**（泰國 `TLTH001` + 5 位、香港 `TLHKHKG009` + 5 位），且異常**只出現在泰國格式**。

初版修法 C 寫「依**公司**登記號碼格式」——**這是錯的**，Toll 一家就有兩種格式，按公司設白名單會立刻衝突。應改為**依格式**（`DocumentFormat`）設定。

## 已量化 B：確定性 —— 不是偶發，是**必錯**（0/10），但錯法不固定

2026-08-05 以 `scripts/tmp-quantify-stage3-nondeterminism.ts` 重跑 Stage 3 各 10 次（Stage 1/2 結果固定，只重跑 Stage 3，不持久化）：

| 檔案 | 版面 | 正確次數 | 抽出值分佈 |
|---|---|---:|---|
| `NEX_RCEX240692,0692A,0692B_9898.pdf` | Nippon 泰國 | **0 / 10** | `EVJ-F9988`×6、`EVJ-F9989`×3、`EVJ-F99898`×1 |
| `NEX_RCEX250017_0394.pdf` | **同一版面** | **10 / 10** | `EVJ-G0394`×10 |

原文為 `EVJ-F9898`。**十次沒有一次命中。**

這推翻了初版的「非確定性、可能偶發」定性 —— 該份是**穩定地錯**，只是錯法在三種之間擺動。同版面對照組則穩定正確。

### 🔑 `EVJ-F99898` 這一次揭示了成因

第 10 次抽出的 `EVJ-F99898` 包含**完整正確的 `9898`**，只是前面多了一個 `9`。三種錯法並列來看：

| 抽出 | 與原文 `9898` 的關係 |
|---|---|
| `F99898` | 正確序列 + 多一個 `9` |
| `F9989` | 交錯數字被重排 |
| `F9988` | 交錯數字被重排 |

模型**看得到**正確的字元序列，錯在**複製含重複交錯數字（`9-8-9-8`）的字串時計數失準**。對照組 `G0394` 無重複交錯字元，10/10 正確。

同一形態亦見於 Toll（見 §已量化 A）：`TLTH00156933` → `TLTH000156933`（連續 `00` 變成 `000`）。**全部指向重複字元的計數，而非影像清晰度。**

⚠️ 據此，原修法選項 **D（提高圖像解析度）應予排除** —— 模型並非看不清。詳見下方修正後的選項表。

### DB 中的獨立佐證

`_9898` 這份在 DB 有**兩筆不同時間的提取**（重複上傳），可作為重跑之外的獨立樣本：

| 提取時間 | 抽出值 |
|---|---|
| 2026-08-04 04:00:14 | `EVJ-F9988` |
| 2026-08-04 06:38:32 | `EVJ-F9989` |

**兩次都錯，且錯法不同** —— 與重跑得到的分佈一致，交叉印證了「穩定地錯、錯法擺動」的定性。

### 副帶觀察

`_9898` 第 6 次的執行同時多抽了一筆 `VAT 7%` 明細（5 筆、合計 7,169），即 [FIX-166](FIX-166-vat-extracted-as-line-item-charge.md) 的形態在此份的發生率為 **1/10**。兩個缺陷可在同一次執行中並發。

## 已量化 C：修法 B（檔名交叉比對）的可行性 —— 98.4% 通過

修法 B 的前提是「檔名尾碼可作為校驗依據」。初版把「並非所有檔名都含號碼」列為風險但未量化。實測全庫 645 份文件：

| 項目 | 份數 | 佔比 |
|---|---:|---:|
| 可取出檔名尾碼且有號碼（可校驗母體） | 378 | — |
| 號碼**包含**檔名尾碼 → 放行 | 372 | **98.4%** |
| 不包含 → 觸發降級 | **6** | **1.6%** |
| 檔名無數字尾碼（此法不適用） | 147 | — |

**誤報率是可接受的**：僅 1.6% 會被降級，而這 6 筆中多數看得出是真問題：

```
NEX_RCEX240692,0692A,0692B_9898.pdf   號碼=EVJ-F9989      尾碼=9898   ← 真陽性（本 FIX 主案例）
NEX_RCEX240692,0692A,0692B_9898.pdf   號碼=EVJ-F9988      尾碼=9898   ← 真陽性（同上，另一次提取）
RIL_RCIM250020_14387.pdf              號碼=0014397        尾碼=14387  ← 極可能真陽性（14397 vs 14387）
DHL_RCEX250281,0282_37434.pdf         號碼=HKGIR027373434 尾碼=37434  ← 待判（初版列為「原文找不到相近值」之一）
CARGO LINK_HEX240655B_09047.pdf       號碼=CLLAEI2409352  尾碼=09047  ← 疑為不同編號體系，可能誤報
RIL_RCIM250316_22021.pdf              號碼=Q20221         尾碼=22021  ← 疑為不同編號體系，可能誤報
```

即最壞情況下誤報 2 / 378 = **0.5%**，換得攔下至少 3 筆真錯誤。

⚠️ 但這 378 份的「通過」只證明**號碼含檔名尾碼**，不證明號碼完全正確 —— 前綴部分（如 `TLTH001` 的 `0` 個數）不在檔名中，**此法攔不到 §已量化 A 的 5 筆 Toll 異常**（它們的尾碼都在）。B 與 C 必須並用，不可互相取代。

## 仍待量化

1. ~~**Toll 四筆**尚未重跑~~ —— 已由 §已量化 A 取得**影響面**（5/51）。但**確定性**（同一份重跑會不會再錯）仍未測
2. 「多插 0」與「數字錯位」是否為同一成因的兩種表現 —— 目前為推論
3. `CEVA LOGISTICS_RCEX240706_00543.pdf` 曾記為多插 0、重跑後正確，屬**同版面時對時錯**，與本份的 0/10 不同，需獨立量化
4. §已量化 C 中 3 筆「待判／疑為不同編號體系」需人工核對發票原文，以定出修法 B 的真實誤報率

⚠️ **不可用「重新處理文件」的方式重跑** —— `extraction_results` 對 document 有唯一約束且採 upsert，會**覆蓋**既有結果並銷毀證據。應直接呼叫 Stage 3、不持久化（`Stage3ExtractionService.execute()` 在**不傳 `documentId`** 時為純讀取，其唯一寫入路徑 `recordExtractionFeedback` 的守衛即為 `input.documentId`）。

⚠️ 每次重跑產生 Azure OpenAI 費用。

## 修法選項（待量化後拍板）

| 選項 | 作法 | 風險 |
|---|---|---|
| **A. 自我校驗** | Stage 3 Prompt 要求回傳號碼時同時回報字元數，或要求逐字元覆述一次 | 增加 token；對非確定性錯誤不保證有效 |
| **B. 檔名交叉比對** | 檔名常含發票號碼尾碼（`_9898`、`_00543`），以此校驗抽出值；不一致時降級 | 適用 378/645 份；誤報率實測 ≤0.5%（見 §已量化 C）。**攔不到前綴錯誤**（Toll 那 5 筆） |
| **C. 格式白名單** | 依**文件格式**登記號碼樣式（泰國 `TLTH001`+5 位＝12 字元、香港 `TLHKHKG009`+5 位），長度或樣式不符即降級 | 🔴 初版寫「依**公司**」是錯的 —— Toll 一家就有兩種格式（見 §已量化 A）。需維護每個格式的規則；新格式無規則可用 |
| ~~**D. 提高圖像解析度**~~ | ~~對號碼區域以更高 DPI 重讀~~ | 🔴 **已排除** —— `EVJ-F99898` 那次證明模型看得到完整正確序列，只是多複製一個字元。提高解析度不解決計數問題 |

### 建議

**B 與 C 並用，缺一不可。**（初版寫「B 優先，C 次之」，量化後發現兩者攔截的是**不相交**的錯誤類型。）

| 修法 | 攔得到 | 攔不到 |
|---|---|---|
| **B** 檔名交叉比對 | 尾碼被改動的錯誤（EVJ 案例） | **前綴**錯誤 —— Toll 那 5 筆的尾碼都正確 |
| **C** 格式白名單 | 長度／樣式偏離（Toll 多插 0） | 長度不變的字元錯位（EVJ 的 `9898`→`9989`） |

兩者的覆蓋恰好互補：EVJ 只有 B 攔得到，Toll 只有 C 攔得到。**單用任何一個都會漏掉本 FIX 已知的一半案例。**

- **A（自我校驗／逐字元覆述）效果存疑** —— 量化把問題定位在「複製含重複交錯數字的字串時計數失準」，這類錯誤**模型自己察覺不到**（它認為自己讀對了）。要求覆述，它很可能覆述出同樣的錯值。除非要求輸出每個字元的位置索引，但那會大幅膨脹 Prompt 與輸出
- **實作成本**：C 需要一份「格式 → 號碼樣式」對照表。目前僅 Toll 兩種格式有明確規律可登記，其餘公司需逐一觀察，**建議先只為已知有問題的格式建規則**，不追求全覆蓋

B 與 C 都只做**偵測與降級**，不嘗試自動更正 —— 猜錯的號碼比留空更難發現。

## 證據強度說明（2026-08-05 更新）

Nippon 那筆有檔名 `_9898` 作為第三方佐證，判定可靠。Toll 的形態一致（固定前綴後多插一個 `0`），且 §已量化 A 顯示同格式另有 46 份**全部正確**，構成強對照組。

初版寫「**『有多少份也有此問題』不可靠**」—— 此限制對 Toll **已解除**：號碼樣式的偏離（12 字元 vs 13 字元）可由程式判定，不需視覺核對，故 5/51 這個數字可靠。

仍存在的限制：

1. **對非固定格式的公司仍不可靠** —— 沒有樣式規律就無法用程式判定，只能靠視覺核對，而核對者與被核對的提取同為視覺模型
2. §已量化 C 的 6 筆中有 3 筆未判定真偽，故 B 的誤報率為區間（0.5%–1.6%）而非確數

## 驗證方式

修法 C 屬確定性規則，可直接以既有資料驗證，**不需重跑 Stage 3**：

1. 以 §已量化 A 的 5 筆為正樣本：套用 C 後全部須被降級
2. 以同格式其餘 46 筆為負樣本：不得有任何一筆被誤降級

修法 B 同理：

3. 以 §已量化 C 的 6 筆為正樣本、372 筆為負樣本驗證

修法 A（Prompt 約束）才需重跑：

4. 以相同的 N 次重跑比較 §已量化 B 的正確率
5. 逐份確認號碼與發票原文逐字元一致（**不是只看「有沒有抽到號碼」**）
