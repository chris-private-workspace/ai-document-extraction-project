# FIX-152: DHL 多 shipment 發票的費用合計洩漏到第一組明細 —— 跨 shipment 重複計費

> **建立日期**: 2026-08-01
> **發現方式**: 追查 FIX-151 對帳落差時，逐份檢視 DHL 的行項合計與 `total_amount` 差額
> **影響頁面/功能**: Stage 3 提取 → 行項目分組 → 模板實例列金額
> **優先級**: 高（**金額錯誤**：同一筆運費在兩個 shipment 各算一次，首組虛增。目前被對帳閘攔在 `FULL_REVIEW`，未流出，但無任何訊號指出錯在哪一列）
> **狀態**: 📋 規劃中（根因已確認、修復方案待拍板）
> **相關**: [CHANGE-113](../feature-changes/CHANGE-113-line-item-group-key-multi-shipment-invoice.md)（引入分組機制，其驗收抽樣通過）、[FIX-146](FIX-146-change113-annotations-not-effective-on-azure.md)、[FIX-147](FIX-147-stage3-wrapped-line-description-misjoin.md) / [FIX-151](FIX-151-reconcile-uses-tax-inclusive-total.md)（對帳閘，本問題目前唯一的攔截點）

## 問題描述

`DHL_RCIM250111_28699.pdf` 涵蓋兩個 shipment。2026-07-31 03:17 的提取結果：

| groupKey | 描述 | 提取值 | 正確值 |
|---|---|---:|---:|
| `RCIM-25-0111` | EXPRESS WORLDWIDE nondoc | **2,557.50** ❌ | 247.50 |
| `RCIM-25-0111` | FUEL SURCHARGE | 69.92 ✅ | 69.92 |
| `RCIM-25-0113` | EXPRESS WORLDWIDE nondoc | 2,310.00 ✅ | 2,310.00 |
| `RCIM-25-0113` | FUEL SURCHARGE | 652.58 ✅ | 652.58 |

首組多算了 2,310.00 —— 那正是**第二組的運費**。同一筆錢在兩個 shipment 各出現一次。

分組本身完全正確：`groupKey`、`groupSourceRef`、筆數、其餘三筆金額都對。**錯的只有第一組的第一筆金額。**

### 正確值如何確定

不是推測，是三條獨立算術互相印證（取自該次的 `gpt_response`）：

```
頂層 fields.express_worldwide_nondoc = 2557.50      ← 全發票運費合計
頂層 fields.fuel_surcharge           = 722.50       ← 全發票燃油合計
頂層 fields.total_amount             = 3280.00      = 2557.50 + 722.50 ✓

明細 FUEL:    69.92 + 652.58 = 722.50 = 頂層 fuel_surcharge ✓ 拆分正確
明細 EXPRESS: 2557.50 + 2310.00 = 4867.50 ≠ 頂層 2557.50   ✗ 首筆是合計本身
        ⇒ 首筆正確值 = 2557.50 − 2310.00 = 247.50
        ⇒ 修正後合計 = 3280.00 = total_amount ✓ 精確吻合（差 0）
```

`unitPrice` 自證同一件事：第二組 `3 × 770.00 = 2310.00` 精確；首組 `4 × 639.375 = 2557.50`，單價出現三位小數 —— 那是拿 2,557.50 ÷ 4 反推的產物，不是發票印出的單價。

## 根本原因

### 這**不是**迴歸

Azure DEV 上這份文件共 9 次提取。同一份 PDF、同一套 DHL 專屬 prompt，結果在正確值與合計之間反覆跳動：

| 提取時間 | prompt 長度 | 首組 EXPRESS | 首組 FUEL | 判定 |
|---|---:|---:|---:|:--|
| 07-22 05:36 | 4514（尚無彙總排除規則） | 2557.50 | 722.50 | ✗ 兩項都是合計 |
| 07-22 05:43 | 4514 | 3280.00 | — | ✗ 讀成 `total` |
| 07-30 02:32 | 5690 | **247.50** | 69.92 | ✅ |
| 07-30 07:16 | 5690 | 2557.50 | 699.20 | ✗ |
| 07-30 07:58 | 5690 | **247.50** | 69.92 | ✅ |
| 07-30 09:34 | 5690 | 2557.50 | 699.20 | ✗ |
| 07-30 09:40 | 5690 | 2557.50 | 69.92 | ✗ |
| 07-30 10:25 | 6371 | **247.50** | 69.92 | ✅ ← CHANGE-113 驗收 |
| 07-31 03:17 | 7179 | 2557.50 | 69.92 | ✗ |

同一 prompt 版本（5690）連跑 5 次：**2 對 3 錯，命中率 40%**。

CHANGE-113 的驗收**有**逐筆核對金額（該文件 §驗收 11 列出 247.50 + 69.92 = 317.42、模板列狀態 `VALID`），那一次確實是對的。缺口不在核對的細緻度，而在**單次抽樣無法驗證非確定性行為** —— §驗收 7 的「連跑 3 次一致」測的是本機更早的版本，未涵蓋此形態。

### Prompt 的內在矛盾

現行 DHL COMPANY prompt（`prompt_configs.id = 'change113-dhl-stage3-001'`）同時要求兩件事：

| 位置 | 要求 | 在多 shipment 發票上的正確答案 |
|---|---|---|
| `--- Field Extraction Requirements ---` | 提取頂層欄位 `express_worldwide_nondoc` | **2,557.50**（全發票合計，即 Service Sub Total） |
| `## Line item rules` 第 2 條 | `NEVER emit aggregate rows as line items. Ignore "Service Sub Total ..."` | 明細列**不得**使用 2,557.50 |

**同一個數字在頂層是必須寫出的答案、在明細列是明令禁止的答案。** 模型在同一次生成中先寫 `fields.express_worldwide_nondoc = 2557.5`，緊接著寫 `lineItems[0].amount` —— 那個值就在上下文最近處。

四項觀察與此假說一致，且沒有與之相斥的觀察：

1. 洩漏**只發生在第一筆**（最先寫出的 lineItem），後續各組都正確
2. 洩漏值**恰好等於**對應的頂層欄位值，不是任意錯數
3. 燃油也會洩漏：`DHL_RCIM250291_20411.pdf` 07-30 那次首組 FUEL = **5,949.36** = 該發票四組燃油之和（2086.84 + 672.41 + 2159.81 + 1030.3）
4. 錯誤的 `unitPrice` 是模型為維持 `qty × unit = amount` 自洽而反推的

> 這解釋了為何加強「排除彙總列」的字面禁令收效有限：禁令針對的是**表格上的彙總列**，而模型洩漏的是**它自己剛寫下的頂層欄位值**。兩者是不同的來源。

## 可用的確定性校驗規則

由上述根因導出一條**不依賴猜測**的檢查式：

```
對每個頂層費用欄位 F：
    Σ(該類 lineItems 的 amount) 必須等於 F
若不等，且 F 恰好等於其中某一列的 amount：
    該列的正確值 = F − Σ(其他同類列)
```

三個實例全部滿足（含一個由它預測、後續提取實際驗證的案例）：

| 文件 / 次數 | 頂層欄位 F | 其他同類列之和 | 推得正確值 | 佐證 |
|---|---:|---:|---:|---|
| `RCIM250111` 07-31 | `express_worldwide_nondoc` 2557.50 | 2310.00 | **247.50** | 07-30 三次實際提取皆為 247.50 ✅ |
| `RCIM250291` 07-30 | `fuel_surcharge` 5949.36 | 3862.52 | **2086.84** | 07-31 該筆實際提取即 2086.84 ✅ |
| `RCIM250291` 07-31 | `express_worldwide_nondoc` 19997.85 | 12983.25 | **7014.60** | 修正後合計 = 25947.21 = `total_amount` ✅ |

比用 `total_amount` 反推更精準：它是**逐費用類別**的，不需要整份發票的其他欄位都正確。

## 影響範圍

2026-08-01 Azure DEV 全量掃描（每個檔名取最新一次提取）：

| 項目 | 數量 |
|---|---:|
| 有 ≥2 筆行項目且有 `total_amount` 的文件 | 271 份 |
| 其中**多 shipment 分組**（>1 組） | **6 份** |
| 行項合計與 `total_amount` 有落差 | 62 份 |
| 命中本問題形態 | **2 份確鑿**（皆 DHL） |

確鑿的 2 份：`DHL_RCIM250111_28699.pdf`、`DHL_RCIM250291_20411.pdf`。

⚠️ **樣本命中率不等於發生率**。母體僅 6 份多 shipment，且問題本身是非確定性的 —— 同一份文件重跑就可能翻轉。以 40% 的單次命中率推估，任一份多 shipment 的 DHL 發票每次提取都有相當機率出錯。

### 掃描判準的已知界限（誠實記錄）

初版判準（`Σ其他同描述列 == 整份落差`）另外命中 `DHL_RCIM250246_94867.pdf`，推出「該列應為 0」—— **這是誤判**。該份實際是兩組明細完全重複（382.20 + 57.33 各出現兩次），屬另一種錯誤形態，不在本 FIX 範圍。

另有 `DHL_RHIM250034_74315.pdf`（落差 8,625.72、10 筆 4 組）不符任何既有判準，需個別判讀，同樣不在本 FIX 範圍。

上文「可用的確定性校驗規則」改以**頂層欄位**為基準，不受此誤判影響 —— 該份的頂層欄位與明細之和關係需另行查證後才能判斷是否命中。

## 修復方案（待拍板）

| 選項 | 做法 | 優點 | 代價 / 風險 |
|---|---|---|---|
| **A. Prompt 消除矛盾** | 明確告知頂層 `fields.*` 是**全發票合計**、`lineItems` 是**逐列明細**，並要求輸出前自我校驗「同類明細之和 == 對應頂層欄位」 | 不動程式碼；直指根因（矛盾本身） | 仍是機率性的，無法保證；需多次重跑量測才知改善幅度 |
| **B. 後置偵測 + 標記** | Stage 3 後套用上述校驗規則，不改金額，把「哪一列、現值、推算值」寫入診斷欄位並強制 `FULL_REVIEW` | 安全，不竄改模型輸出；審核者直接看到錯在哪一列（目前完全沒有這個訊號） | 仍需人工改值 |
| **C. 後置自動校正** | 偵測到即自動改寫該列金額 | 全自動 | **不建議** —— 判準誤判時會改壞資料（見 `RCIM250246` 誤判實例）；系統自行竄改提取結果，且本專案 `extraction_results` 無版本歷史可回溯 |
| **D. 對帳失敗時重試 Stage 3** | 校驗不過就重跑，取通過的結果（最多 N 次） | 利用非確定性本身：單次 40% → 重試 3 次約 87% | 增加 token 成本與延遲；屬管線行為變更，觸及 **H1**，需先評估 |

**建議：A + B 併行**。A 針對根因降低發生率，B 保證即使再發生也能被指名道姓地看見。D 待 A 的量測結果出來後再評估是否需要。C 不採用。

> ⚠️ A 與 B 都需要在**多次重跑**下量測，不可再以單次通過作為驗收依據 —— 那正是 CHANGE-113 驗收留下缺口的原因。
