# 歷史資料語義斷點登記簿

> **用途**：記錄「同一個欄位在不同時期代表不同意思」的時間點。
> **何時必讀**：對 `extraction_results` / `documents` 做**跨時間統計**之前。
> **這不是缺陷清單** —— 登記的多數項目**已經修好了**。正因為修好了，同一欄位的歷史值才會跨越語義邊界，而舊值不會被回填。

---

## 為什麼需要這份文件

修復一個寫入端的缺陷，只改變**之後**寫入的值。資料庫裡**既有**的值仍是舊語義，而且本專案的 `extraction_results` 沒有版本欄位可供區分（見 §相關陷阱）。

於是任何「拉全部歷史資料算比例」的分析，都會把已修復的缺陷算成現行狀態。

**實例（2026-08-01，FIX-148 影響評估）**：初版評估拉了全部 802 份，算出「啟用後需人工介入 +411%」，且降級全部由 `isNewFormat` 觸發。以 FIX-124 為界切分後，真實數字是 **+123%** —— **誤差 3 倍**，方向與結論都會被誤導。

### 1. `isNewFormat` — FIX-124（2026-07-21）🟢

**斷點前**：`jitCreateFormat` 撞唯一鍵 `(companyId, INVOICE, GENERAL)` 時**沿用既有格式的 id**，而 `resolveFormatId` 第 5 步仍無條件回傳 `isNewFormat: true`。產生「**有 formatId、卻標記為新**」的組合 —— 同一個已建檔格式被反覆判為「新」。

**斷點後**：FIX-124 改為撞唯一鍵時回傳**無 id**（語義是「這是新版面，但尚未登記為 DocumentFormat」）。該組合不再出現。

**查證（Azure DEV，2026-08-01）**：

| 事實 | 值 |
|---|---|
| 全庫判 `isNewFormat = true` | 471 份 |
| 其中 `formatId` 指向**早已存在**的格式 | **370 份**（最久相隔 30 天） |
| 「格式早已建立（>1 小時）卻標記為新」的**最近一筆** | **2026-07-21 08:55** |
| 該日之後 11 天（至 2026-08-01）的同類記錄 | **0 筆** |
| 近期樣本 | 全部是「格式與提取同一分鐘建立」的真新建 |

最極端的例子：`CEVA Logistics Original Invoice` 51 份**全部**判為新格式，且 `distinct formatId = 1`。

**分析時怎麼做**：統計 `isNewFormat` 一律以 **2026-07-22** 為起點，或改用「該 `formatId` 的 `created_at` 與本次提取時間是否在同一分鐘內」作為「真新建」的判準 —— 後者不依賴日期切分，較穩健。

---

### 2. `configSource` — 從未寫入 `stage_2_result` 🟢

`Stage2FormatResult` 型別有 `configSource` 欄位，`stage-2-format.service.ts` 也回傳它，但**落到 `extraction_results.stage_2_result` 的 JSON 裡沒有這個 key**。

**查證**：802 份有路由結果的文件，`stage_2_result` 缺 `configSource` 者 **802 / 802**（100%）。`stage_1_result` / `stage_2_result` 同樣沒有 `success` 欄位。

**後果**：任何依賴 `configSource` 的分析都無法從既有資料進行 —— 包括 `applyRoutingStrategy` 的「配置由 LLM 推斷 → 降級」這一項。FIX-148 的影響評估因此**無法涵蓋該條件**，其結論只能表述為「真實衝擊 ≥ 已量化的數字」。

> 注意這與斷點 1 不同：不是語義改變，而是**欄位根本沒進資料庫**。分析前先確認欄位真的存在，不要因為型別定義有就假設資料有。

---

### 3. `lineItemTotalReconciliation` — FIX-147 引入（2026-07-31）🟡

FIX-147 之前的提取結果**沒有這個欄位**。`confidence-v3-1.service.ts` 已明確處理：「舊資料無此欄位 → `undefined` → 不觸發」。

**分析時怎麼做**：`mismatch` 缺值代表「當時沒對過帳」，**不等於**「對過帳且相符」。把兩者混為一談會低估歷史的對帳不符率。

證據等級為 🟡：依據代碼註解與 FIX-147 文件，未另做資料層計數。

---

### 4. `totalSource` 新增 `'subtotal'` — FIX-151（2026-08-01）🟡

FIX-151 之前，對帳基準恆為 `total_amount`（含稅）。之後，當行項合計與 `subtotal`（不含稅）精確吻合時改以 `subtotal` 為基準並判定相符。

**後果**：同一份文件在斷點前後可能得到不同的 `mismatch` 值，而**分毫未變的是明細本身**。跨斷點比較「對帳不符率」會把一次判定規則的修正誤讀為資料品質變化。

證據等級為 🟡：代碼已合併（PR #194），但**尚未部署 Azure DEV** —— 斷點在 Azure 資料上尚未發生。部署後請回來把日期補實。

## 相關陷阱（不是語義斷點，但同樣會誤導跨時間分析）

| 陷阱 | 說明 |
|---|---|
| **提取結果會被覆蓋** | `extraction_results` 對 `document_id` 有唯一約束且採 upsert。重新處理**覆蓋**上一次的結果，系統沒有提取歷史。看到的「歷史」其實是「每份文件最後一次」的快照。（治本＝CHANGE-114） |
| **同一份 PDF 會有多個 document** | 使用者重新上傳會產生新 `document`，因此同一檔名可能有多筆提取結果，時間跨度很長。全庫 869 份文件只有 337 個相異檔名。統計時決定要「每檔名取最新」還是「全部計入」，兩者結論不同。 |
| **LLM 提取本身不具決定性** | 同一份文件、同一套 prompt，多次提取結果可能不同（見 FIX-152：DHL 多 shipment 的命中率約 40%）。單次抽樣不能作為驗收依據。 |

## 如何新增條目

發現「某欄位的歷史值跨越了一次語義修復」時：

1. 找出**斷點日期**：對應的 FIX/CHANGE 完成日，並以資料驗證（查「最後一筆舊語義記錄」的時間）
2. 標明**證據等級**：🟢 資料層完整查證 ／ 🟡 代碼或文件佐證 ／ 🔴 推測
3. 寫明**分析時怎麼做** —— 這是本文件的實際價值所在，不要只描述現象
4. 若該欄位有「不依賴日期切分」的替代判準（如斷點 1 的同分鐘比對），優先寫出來

> ⚠️ 斷點日期用**代碼完成日**只是起點。本專案 Azure 部署為手動，線上生效時間可能晚於代碼日 —— 以資料查出的「最後一筆舊語義記錄」為準。
